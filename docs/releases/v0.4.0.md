# Listing Guard v0.4.0

Changes since v0.3.0. v0.4.0 adds the trademark risk check, the `batch-check` job and the pack identity that lets
several analyses share one service. The rule checks (`POST /api/v1/checks`) keep their request, response and results.

**Read the [upgrade notes](#upgrade-notes) before you deploy.** This release changes the database in ways that an older
image cannot undo.

## What is new

### Pack identity (ADR-010, migrations V7 to V14)

Rulesets and checks now carry the analysis pack that produced them (`pack_id`, `analysis_version`), and the ruleset
registry and the result cache are keyed by it. This is what lets a new analysis (the trademark check is the first) live next
to the rules without touching their cache.

- V7 adds the columns and backfills them. V8 to V14 make them mandatory, replace the registry identity
  `(marketplace_code, version)` with `(pack_id, marketplace_code, version)`, replace the completed-result cache index with
  one that also covers the pack, the ruleset version and the analysis version, and make
  `listing_check.ruleset_version_id` mandatory.
- `/api/v1/checks` does not change: same request, response, content hash, `rulesetVersion`, `analysisVersion` and cache
  hits. The Etsy and Amazon rulesets (`etsy-2026-11`, `amazon-2026-11`) are identical to v0.3.0.

### Trademark risk check (ADR-009)

`POST /api/v1/trademark-checks` compares the text of a listing with a catalog of marks and reports possible references;
`GET /api/v1/trademark-checks/{id}` reads a stored result. It is a separate check with its own endpoint, result tables and
cache. **It is off until you load a catalog and name it in the configuration**, and `/checks` is not affected in any state.

- **Matching.** Exact, phrase and fuzzy matching (final score: optimal string alignment, `osa-similarity-1`) on text
  normalized with offsets. Context rules cover a place name next to a sport term (`geo_sport_combination`), a phrase that is
  only color and pattern words (`pure_color_description`, always `LOW`) and a match inside a color phrase
  (`insideColorPhrase`, which explains a finding and never lowers it). Etsy reads `title`, `description` and `tags`;
  Amazon reads `title`, `description`, `brand`, `bullet_points` and `search_terms`.
- **Explainable evidence.** Each finding carries the field, the span (`start`, `end`), the snippet, the matched mark, the
  match type, the score, the ids of the source records, the rule ids it won over, and a Vietnamese message and suggestion.
  The result carries `completeness` and a `riskLevel`. A failing rule gives `INCOMPLETE` and keeps the findings already
  established; a risk that cannot be determined is `UNKNOWN`, never `LOW`.
- **Disclaimer.** Every result carries a `disclaimer`: it is a reference warning, not a legal conclusion.
- **Versioned ruleset.** `trademark-risk-2026-11` holds every threshold, word list, risk level and message. All of its
  sources are marked `unverified`.
- **Offline, versioned catalog** (V15, V16, V18). Catalog versions live in PostgreSQL (`pg_trgm`) and are append-only: a
  changed file, filter or normalization is a new version, never an edit. You load them with the one-shot `trademark-import`
  job from `catalogs/manifest.yaml` and local files in `catalogs/raw/`, and you name the active version in
  `listing-guard.trademark.catalog-version` (never "latest"). The state is `DISABLED`, `READY` or `REFUSED`; a catalog
  imported with other normalization settings is refused at start-up and the API still starts.
- **Several sources and large files** (ADR-009, PR A2b). A manifest entry may list `sources:`, each with a `source_key`
  (stored ids are `<source_key>:<id>`), and the import reads each file as a stream through a temporary table in one
  transaction, so its memory does not depend on the size of the file. V18 records one row per data file.
- **Retention** (V17). Only a hash of the listing and short evidence snippets are stored, for 30 days
  (`listing-guard.trademark.retention.period`). An expired result is treated as absent when read, and a scheduled cleanup
  deletes it.

### Batch check

The one-shot `batch-check` job checks a whole export file (an Etsy CSV, an Amazon flat file) with the rules and the trademark
check, for a client you name, and writes `findings.csv`, `listings.csv` and `summary.html`. It reads the file as a stream,
maps its columns to the standard input with a YAML mapping, and calls the same services as the two endpoints, so its results
are the API's results. It needs no network and no model; a row that cannot be read is reported with its line and the batch
goes on. `--label-column` adds a measurement on a small labelled set (not an accuracy). See
[docs/batch-check.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/batch-check.md). The two example mappings carry column names nobody has verified.

### Embeddings and the analyzer groundwork (ADR-011, ADR-012)

- An optional embedding provider backed by the Google Gemini API (`gemini-embedding-2`, 768 dimensions), next to Ollama.
- Retrieval and `eval-retrieval` refuse (`corpus-model-mismatch`) while a stored document was embedded with another model.
- The building blocks of the policy analyzer: the `LlmProvider` contract, a scripted provider for tests, the policy finding
  parser and the `CitationVerifier`. **No call to a real model is implemented** and there is no analyzer endpoint.

### Build, release and project

- ADR-008 to ADR-012 are in `docs/adr/`.
- The release workflow now builds the image, scans it with Trivy and publishes it only when the scan finds no fixed
  critical vulnerability. The repository gains Dependabot updates and a CodeQL workflow.
- The unused Redis service is gone from `docker-compose.yml`.
- The container image is built and runs on Eclipse Temurin 24 (it was 21). The code still targets Java 21.
- springdoc-openapi is 2.10.0 (it was 2.8.17). `docs/api/openapi.json` has the two new trademark operations.

## Breaking changes

- **A write that omits `pack_id` now fails.** From V8, `pack_id` is `NOT NULL` without a default on `ruleset_version` and
  `listing_check`, and `analysis_version` and `listing_check.ruleset_version_id` are `NOT NULL`. The API and the jobs name
  their pack and are not affected; a script or a tool of yours that inserts into these tables must set the columns.
- **A v0.3.0 (or older) instance cannot write to the upgraded database.** Its inserts omit `pack_id`. Rolling back the image
  does not undo the migrations: see [Rolling back](#rolling-back).
- **Embeddings are off by default.** The provider default changed from `ollama` to `none` (ADR-012). `ingest`,
  `eval-retrieval` and `GET /policies/search` do not work until you set `EMBEDDING_PROVIDER=api` (with
  `LISTING_GUARD_EMBEDDING_API_KEY`) or `ollama`; search answers `503` with `embedding-not-configured` until then. The rule
  checks need neither. With `api` and an empty key the application does not start. In the development compose file Ollama
  now starts only with `--profile ollama`.
- **Mixed embedding models are refused.** After you change the provider or model, run `ingest` again; until then search and
  `eval-retrieval` answer `corpus-model-mismatch`.

## Upgrade notes

Upgrading from v0.3.0 (migrations V1 to V6) applies V7 to V18 the first time v0.4.0 starts. Every step below is from
[docs/deployment.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md), which has the detail.

### What can stop the start

| Migration | When it stops | What to do |
| --- | --- | --- |
| V8 and V14 | A `listing_check` row has `ruleset_version_id` NULL (checks stored before ruleset versions were recorded, V4). Nothing is changed and the API does not start; the error names the number of rows. | Decide by hand, after a backup, to assign the known ruleset version or delete those rows. The queries are in [Checks without a ruleset version](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md#checks-without-a-ruleset-version). Then start again; Flyway repeats V8. |
| V9, V11 | `CREATE UNIQUE INDEX CONCURRENTLY` was cancelled or timed out and left an invalid index, and the failed row stays in the schema history. V10 and V12 then stop too. | Drop only the invalid index and clear the failed history row: [An index build that failed](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md#an-index-build-that-failed). |
| V15 | The database role that runs Flyway cannot create the `pg_trgm` extension, or the server lacks the `contrib` extensions (the `pgvector/pgvector:pg16` image has them). The API does not start and nothing falls back to another matching method. | Allow the role to create the extension. PostgreSQL 16 is the supported version. |
| V16 | A trademark catalog already exists. **This cannot happen when you come from v0.3.0**, which has no catalog tables; it can only happen on a database that ran a build from `main` between the two releases and imported a catalog. | Delete the catalogs and import them again: [Trademark catalog](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md#trademark-catalog-adr-009-pr-a2). |

V17 and V18 only add tables (V18 also copies the facts of each existing catalog version into the new table).

### Upgrade a single instance

An operator-coordinated maintenance window:

1. Back up the database and keep the dump until the new version has proven itself (see
   [Database backup and restore](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md#database-backup-and-restore)). Try the upgrade first on a restored copy of
   that backup.
2. Stop the old process: `docker compose -f docker-compose.prod.yml --profile prod stop api`. **No old instance may run
   or restart from here on.**
3. Set `LISTING_GUARD_VERSION=0.4.0` in `.env` and start it:
   `docker compose -f docker-compose.prod.yml --profile prod pull api` then
   `docker compose -f docker-compose.prod.yml --profile prod up -d --no-deps api`. Flyway runs the migrations before the API
   serves requests.
4. Check the logs and `/health`, and send an identical `/api/v1/checks` request twice: the second answer is `cached: true`
   with the same `checkId`.
5. Only now configure a trademark catalog.

The deployment guide's first step asks that the running release already contains V7. No published release does (v0.3.0 stops
at V6), so here V7 to V14 run in the same start; what the sequence protects against is an older instance writing during or
after the migration, which stopping v0.3.0 first avoids.

### Rolling back

Setting the previous image version does not undo the migrations, and a v0.3.0 instance cannot write after them. To go
back to v0.3.0, restore the pre-upgrade backup before you start it.

### Turning on the trademark check

Nothing changes until you do this. Prepare your catalog data, import it with `trademark-import`, set the printed version in
`listing-guard.trademark.catalog-version` and restart the API: see
[Trademark catalog](https://github.com/thanhdatpb/Listing-Guard/blob/v0.4.0/docs/deployment.md#trademark-catalog-adr-009-pr-a2) and the README. **You are responsible for checking
that the terms of your data source allow this storage and use.**

## Known limits

- **No accuracy has been measured.** The evaluation of the trademark check (ADR-009, PR A4) has not been run, and every
  source status in its ruleset is `unverified`. Treat the result as a reference warning.
- **The catalog is yours.** No trademark data is shipped or downloaded. There is no converter for an official register yet:
  the USPTO converter waits for the official documentation, so you convert your data to the `jsonl-1` format yourself.
- **`docker-compose.prod.yml` does not include the trademark pieces.** It has no `trademark-import` or `batch-check` service
  and does not pass `LISTING_GUARD_TRADEMARK_CATALOG_VERSION` to the `api` service, so the trademark check stays off in the
  packaged production setup until you add them. The development `docker-compose.yml` shows both.
- **Not built:** the policy analyzer (no call to a real model, no endpoint), the image checker (ADR-008, deferred) and the
  retrieval evaluation (it needs a real run with an embedding provider, so there is no recall figure).
