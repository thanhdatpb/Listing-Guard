# Listing Guard v0.5.0

Released 2026-11-05. Changes since v0.4.0. v0.5.0 adds client plans with a monthly quota, optional fix suggestions with a
publish readiness score, an optional web console with a Check listing editor, and a converter for USPTO daily trademark
files. **Everything new is off by default**: a deployment that changes no setting behaves as it did on v0.4.0, and
`POST /api/v1/checks` and `POST /api/v1/trademark-checks` keep their requests, responses, cache identities and results.

**Read the [upgrade notes](#upgrade-notes) before you deploy.** This release adds the migrations V19, V20 and V21. They
are additive, but an older image does not undo them.

## What is new

### Client plans and a monthly quota (ADR-013)

Each client now has a plan (`FREE`, `SELLER` or `PRO`) that decides which packs it may use and how many results it may
store per UTC month. **It is off by default** (`listing-guard.plans.enabled=false`); with the default, nothing about a plan
is read, written or enforced and the API behaves as before.

- **Unit.** One unit is one new result that is stored, per endpoint. A result answered from the cache (`cached: true`), a
  `GET`, an `INCOMPLETE` trademark result and a refused request cost nothing. A full check of one listing, `/checks` plus
  `/trademark-checks`, is two units. Seed (V19): `FREE` 20 units and `listing-rules`; `SELLER` 1000 units and
  `listing-rules`, `trademark-risk`, `batch`, `sheet-connector`; `PRO` 6000 units and all five packs. The numbers are rows
  of the table `plan`, so an operator can change them with an `UPDATE`.
- **Order.** The pack is checked first (`403 plan-not-allowed`), then the cache, then the quota (`429 quota-exceeded`, with
  `plan`, `quota`, `used`, `resetAt` and **no `Retry-After`**), then the analysis; the unit is counted in the transaction
  that stores the result, so concurrent requests cannot take a client past its quota and two identical requests cost one.
- **`GET /api/v1/usage`** returns `enforced`, `plan`, `monthlyQuota`, `used`, `remaining`, `periodStart`, `resetAt` and
  `packs`. It is never refused for plan or quota and costs no unit. `docs/api/openapi.json` has it and the new `403` and
  `429` answers.
- **Admin.** `docker compose run --rm admin plan set <client> <FREE|SELLER|PRO>` (audit-logged with the previous and the new
  plan, effective at once); `client list` shows a PLAN column.
- **`batch-check`.** With plans on it is charged like the API. It needs the `batch` pack, stops **at once** with
  `quota-exceeded` (and no report) when no unit is left, and when the quota runs out in the middle marks the rows it could
  not check `QUOTA_EXCEEDED` in `listings.csv` and says how many in `summary.html` and on the console. Rows whose results are
  stored are still answered.
- **Reserved.** `policy-analyzer` (ADR-011 PR 5) and `sheet-connector` (phase 4b) are in the plans and are not enforced yet.
- **Not included.** Billing, payment, a self-service upgrade, a per-pack quota.

Migration V19 adds `plan`, `plan_pack`, `client_usage` and `client.plan_code` (default `FREE`). See
[docs/deployment.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#client-plans-and-the-monthly-quota-adr-013)
and the [integration guide](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/integration-guide.md#plans-and-monthly-quota).

### Fix suggestions and a publish readiness score (ADR-014, part A and API)

The library implementation is in `core` and `rule-engine`. The opt-in API and batch integration is available with
`listing-guard.fixes.enabled=true` (`LISTING_GUARD_FIXES_ENABLED=true`).

- **Fix suggestions.** `Finding` has a new nullable component `fix` (a `FixSuggestion`: an action, a Vietnamese description
  that cites the numbers, and for a replacement the proposed value). Three rules propose one: `title_length` (Etsy and
  Amazon) and `tag_length` propose the value cut at a word boundary within the limit of the ruleset, and `duplicate_tags`
  proposes removing the repeat. Every other rule has none: there is no replacement of words, and a trademark finding never
  gets a suggestion. A suggestion is never applied by Listing Guard.
- **Checked before it is offered.** `RuleEngine.runDetailed` applies each suggestion alone to a copy of the listing and runs
  the whole ruleset again; it drops the suggestion when the problem remains, when a rule fails that did not before, or when
  the copy has more ERROR or WARNING findings (cutting a tag into a tag that already exists would create a duplicate). It
  also returns the ids of the rules that failed. `RuleEngine.run` is unchanged; `/checks` and `batch-check` use it
  when the flag is off and call `runDetailed` only when the flag is enabled.
- **Publish readiness score.** `ReadinessScorer` computes `max(0, 100 - 20 per ERROR - 5 per WARNING - 1 per INFO)` from the
  versioned file `readiness/readiness-2026-11.yaml`. A listing with an ERROR is not ready and never scores above 59; a run
  in which a rule failed has no score. It counts rule findings only and says nothing about trademark risk. The weights are
  the maintainer's choice and are marked `unverified`.
- **Cost.** Verifying suggestions costs one extra rule run per suggestion, paid only by `runDetailed`. On the largest
  listing of the performance test (16 suggestions, an 18 KB description) the average is about 24 ms against a 50 ms budget.
- **API response.** With the flag on, each finding adds `fix` (verified suggestion or `null`); the response adds
  `fixesComputed` and `readiness: {score, ready, status, version}`. With the flag off, it continues to call `run()` and
  emits no new fields. Fixes replace the normalized `finding.value`; tag descriptions name the tag. List indexes count
  the normalized list (trimmed items, blank entries dropped).
- **Stored and cached results.** V20 adds fix columns to `finding` and readiness columns plus `fixes_computed` to
  `listing_check`. No submitted listing is stored, and ruleset hashes and `analysisVersion` are unchanged. A feature-on
  GET of a legacy result returns `fixesComputed: false`, `readiness: null`, and null fixes. A POST cache hit has the
  original request listing and enriches that result only when `fixes_computed=false`; concurrent enrichment is
  idempotent and costs no quota.
- **Batch.** When enabled, `listings.csv` adds `readiness_score` and `ready`; `summary.html` shows ready, scored and
  INCOMPLETE counts and an average over scored listings only. The score counts listing-rules only; clients must display
  trademark risk separately. The API contract is in `docs/api/openapi.json`.

Migration V20 is additive. There is no ruleset change (`etsy-2026-11` and `amazon-2026-11` keep their hash, so no
`analysisVersion` changes), and no new endpoint. See
[ADR-014](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/adr/ADR-014-listing-workspace.md) and the
[integration guide](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/integration-guide.md#optional-fixes-and-readiness-adr-014).

### Magic-link web console (ADR-014 part B)

The optional Thymeleaf console is disabled by default (`listing-guard.console.enabled=false`). When enabled, a single
email form registers or signs in an account, and a first successful sign-in provisions a FREE client. The initial
dashboard shows the account email, plan and usage. This does not change API-key authentication or the API contract.

- `GET /login/verify` only displays a confirmation page, so email security scanners do not consume links. A CSRF-protected
  `POST /login/verify` consumes the single-use token, valid for 15 minutes; the database stores only its SHA-256 hash.
- The fixed link origin is `LISTING_GUARD_CONSOLE_BASE_URL`; spoofed request `Host` headers are ignored. Verify pages set
  `Referrer-Policy: no-referrer`, Tomcat access logs omit query strings, and successful sign-in rotates the session id.
  Session cookies are HttpOnly, SameSite=Lax and Secure by default.
- Login requests are limited to 5 per normalized email and 30 per remote IP per 15 minutes. Only the `dev` profile logs
  magic links. An enabled production console requires an HTTPS base URL and configured SMTP; see
  [deployment](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#optional-web-console-adr-014-b2).
- Migration V21 adds `account`, `login_token` and shared hashed rate-limit state. Tests use a fake `JavaMailSender`; no
  real email service or network is needed. There is no new API endpoint and no OpenAPI change.

### Check listing editor in the console (ADR-014 part B3)

A signed-in console user can type an Etsy or Amazon listing at `/console/check` and check it. It is part of the optional
console: with `listing-guard.console.enabled=false` (the default) none of it exists. It checks and suggests only; nothing is
published, and **the listing you type is never stored**.

- **What you see.** Findings grouped by severity (errors, warnings, information) with the evidence marked; a verified value for
  each fix that has one; the readiness score and the trademark result **side by side, always both**, with the trademark
  disclaimer; and a preview labelled "Simulation". A listing can score well and still be a trademark risk, and the page never
  shows the score alone.
- **Whatever the flag says.** The editor always shows fixes and readiness, even with `listing-guard.fixes.enabled=false`. The
  flag keeps deciding what `/api/v1/checks` and `batch-check` compute and show: turning the console on does not change the API
  response or the batch reports (a test posts a listing in the editor and reads the old shape from the API for the same result).
- **States.** A trademark catalog that is not loaded shows "Trademark check unavailable" and the rule results stay; a plan
  without the `trademark-risk` pack shows a note and the plans that include it; a used-up quota shows the reset date and, as in
  the API, a listing you already checked is still answered; a rule that failed means "Not scored", never a number.
- **Cost.** The text beside the Check button says up to one unit (listing rules) or two (with the `trademark-risk` pack) of the
  monthly quota; a listing already checked is free, and with plans off nothing is counted.
- **Fields.** Title, tags (one per line) and description for Etsy; title, bullet points and description for Amazon; and a
  collapsed "Other listing fields" section with the fields the rules require (it opens when a required field is missing).
  `who_made` and `when_made` are free text; no list of codes is kept. Counters show the limits of the active ruleset.
- **Apply suggestion** only fills the title or a tag with the proposed value; it never checks again, so it costs nothing, and
  you press Check to see the effect. It refuses a field you changed after the check.
- **Preview.** The search result is cut by the style sheet (no character count is assumed) and the product page marks the part
  of the title beyond the ruleset limit. It uses no logo, image, brand color or domain of any marketplace and is not updated
  while you type.
- **Not included.** Saved listings or history, a live preview, applying several fixes at once.

No migration, no new API endpoint and no change to `docs/api/openapi.json`. The page uses two static files,
`/console/editor.css` and `/console/editor.js`, served behind the console sign-in; there is no build step and no Node. See
[ADR-014](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/adr/ADR-014-listing-workspace.md) and
[deployment](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#optional-web-console-adr-014-b2).

### A DEMO trademark catalog

`catalogs/demo/` holds ten invented marks (nothing real) so the trademark panel can be tried locally and shown in
demonstrations. It is never used by default: you import it on purpose, with its own manifest, and point
`TRADEMARK_CATALOG_VERSION` at the version the job prints. Never serve it in a deployment other people use. See
[catalogs/demo/README.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/catalogs/demo/README.md).

### USPTO converter (ADR-009, PR A2b)

The one-shot job `uspto-convert` converts one USPTO Trademark Applications Daily XML file (TDXF, DTD V2.0) that you
downloaded yourself into the `jsonl-1` format that `trademark-import` reads.

```bash
docker compose run --rm uspto-convert --input=uspto/<file.xml> [--output=<name>.jsonl] [--overwrite]
```

- **Unverified against real data.** It was written from the public DTD V2.0 and its element documentation (ADR-009 names
  both, with their URLs and SHA-256) and tested with small synthetic XML. No real USPTO file has been read yet, so run it on
  a real file and read its report before you rely on a catalog made from it. Its status map,
  `uspto-status-map-2026-11.yaml`, is the maintainer's reading of Table 1 of the documentation and is marked `unverified`.
- **Streaming and offline.** The XML is read as a stream (a test converts a file larger than a 32 MB heap), the DTD is never
  loaded and no external entity is resolved. The job makes no network call and imports no catalog. Like the other jobs it
  starts the application, so it needs the database running; it applies pending migrations and registers the trademark
  ruleset as they do.
- **Output.** `<name>.jsonl` and `<name>.jsonl.report.json` in `catalogs/raw/`, written through a `.part` file and renamed
  on success. The report counts the records read, written and dropped (for each reason: a logo-only mark, no mark text, a
  status that carries no status of the mark, a status code that is not listed, and others) and gives the `sha256` to put in
  `catalogs/manifest.yaml`. `catalogs/manifest.yaml` has a commented `sources:` example.
- **One version only.** The file must declare `version-no` `2.0`; another value stops the job and names what it found.
  `USPTO_ALLOW_OTHER_VERSION=true` (`listing-guard.trademark.uspto.allow-other-version`) reads it anyway.
- **Known limits.** A daily file holds changes, not the whole register, and the same serial number can appear several
  times with different statuses. The import keeps the status declared first (`REGISTERED` before `PENDING`), so an old record
  can hide a newer one; "the latest transaction wins" is a later pull request (A2c). The status of each class is ignored.

No migration, no new endpoint and no change to `docs/api/openapi.json`. The compose service `uspto-convert` is in the
`tools` profile of the development `docker-compose.yml` and starts only when you run it. See
[docs/deployment.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#trademark-catalog-adr-009-pr-a2).

### Build, release and project

- ADR-013 (plans and quota) and ADR-014 (Listing Workspace) are in `docs/adr/`; ADR-009 records the USPTO documents the
  converter follows.
- The API now depends on Spring Security, Thymeleaf and Spring Mail (the console), and these are on the classpath whether or
  not the console is enabled. API-key authentication is unchanged.
- The container image is built and runs on Eclipse Temurin 25 (v0.4.0: 24). The code still targets Java 21.
- `docs/api/openapi.json` has `GET /api/v1/usage`, the `403` and `429` answers and, for the opt-in fields, `fix`,
  `fixesComputed` and `readiness`.

## Breaking changes

No breaking HTTP change: plans, fixes and the console are off by default and response additions are additive. For code that
uses the libraries: `Finding` has an eighth component (the seven-argument constructor is kept). Two things an operator may
notice:

- **`admin client list` has a new PLAN column before CREATED.** A script that cuts the columns by position needs updating.
- **`BatchCheckJob` takes a `PlanService`.** This is internal and matters only to code that builds the job by hand.

## Upgrade notes

Upgrading from v0.4.0 applies V19, V20 and V21 the first time v0.5.0 starts. They are additive: V19 and V21 create tables,
V19 adds `client.plan_code` with the constant default `FREE`, and V20 adds columns that are `NULL` or have a constant
default. The detail is in
[docs/deployment.md](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md). **Coming from v0.3.0 or
older?** Read the [v0.4.0 notes](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/releases/v0.4.0.md) first:
V7 to V18 run in the same start, and what can stop the start there still applies.

### What can stop the start

None of V19 to V21 depends on the data you already have. The one new way to stop the start is a setting:

| Setting | When it stops | What to do |
| --- | --- | --- |
| `LISTING_GUARD_CONSOLE_ENABLED=true` in production | Without an SMTP host and sender address, an HTTPS base URL or Secure cookies the application refuses to start. | Set `LISTING_GUARD_CONSOLE_BASE_URL` (HTTPS), `LISTING_GUARD_CONSOLE_MAIL_FROM` and the `SPRING_MAIL_*` values, or leave the console off: [Optional web console](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#optional-web-console-adr-014-b2). |

### Upgrade a single instance

1. Back up the database and keep the dump until the new version has proven itself (see
   [Database backup and restore](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#database-backup-and-restore)).
   Try the upgrade first on a restored copy of that backup.
2. Set `LISTING_GUARD_VERSION=0.5.0` in `.env`, then pull and recreate only the API:
   `docker compose -f docker-compose.prod.yml --profile prod pull api` and
   `docker compose -f docker-compose.prod.yml --profile prod up -d --no-deps api`. Flyway runs V19 to V21 before the API
   serves requests.
3. Check the logs and `/health`, and send an identical `/api/v1/checks` request twice: the second answer is `cached: true`
   with the same `checkId`. The cache identity of a check does not change in this release, so results stored by v0.4.0 are
   still answered from the cache.
4. Every new feature is still off. Turn on only what you need, below.

### Turning on the new features

Nothing changes until you do this. Each setting is read at start-up, so restart the API after changing it.

| Feature | Setting | Before you turn it on |
| --- | --- | --- |
| Plans and monthly quota | `LISTING_GUARD_PLANS_ENABLED=true` (`PLANS_ENABLED=true` in the development compose file); set it for `batch-check` too | Every existing client is `FREE` after V19: 20 units a month and no trademark, batch or sheet pack. Give each client its plan first with `docker compose run --rm admin plan set <client> <FREE\|SELLER\|PRO>`. Usage is counted only while plans are on. |
| Fix suggestions and readiness | `LISTING_GUARD_FIXES_ENABLED=true` in `.env` (`FIXES_ENABLED=true` in the development compose file); for `batch-check` pass it to one run with `docker compose run --rm -e LISTING_GUARD_FIXES_ENABLED=true batch-check ...` | Clients that show the readiness score must show the trademark result next to it. See [Fix suggestions and readiness](https://github.com/thanhdatpb/Listing-Guard/blob/v0.5.0/docs/deployment.md#fix-suggestions-and-readiness-adr-014). |
| Web console | `LISTING_GUARD_CONSOLE_ENABLED=true`, with `LISTING_GUARD_CONSOLE_BASE_URL` (HTTPS), `LISTING_GUARD_CONSOLE_MAIL_FROM` and the `SPRING_MAIL_*` values | `deploy/env.prod.example` lists them. Production needs HTTPS and SMTP. |
| USPTO converter | Run `uspto-convert` on purpose (development compose file, `tools` profile) | Unverified against real data; read its report before you rely on a catalog made from it. |

### Rolling back

Setting the previous image version does not undo the migrations. To go back to v0.4.0, restore the pre-upgrade backup before
you start it, as the deployment guide describes. The lighter way back is a setting: with plans off the application ignores
the plans, and with the console off none of it exists. Nothing else changes while the three settings stay at their defaults.

## Known limits

- **No accuracy has been measured.** The evaluation of the trademark check (ADR-009, PR A4) has not been run, and every
  source status in the trademark ruleset, the readiness weights and the status map of the USPTO converter are `unverified`.
  Treat the result as a reference warning.
- **The USPTO converter has never read a real file**, and "the latest transaction of a serial number wins" (PR A2c) is not
  built, so a catalog made of daily files can hold an outdated status. The catalog stays yours: no trademark data is shipped or
  downloaded, and you are responsible for checking that the terms of your data source allow this storage and use.
- **`docker-compose.prod.yml` does not include the trademark pieces.** It has no `trademark-import`, `batch-check` or
  `uspto-convert` service and does not pass `LISTING_GUARD_TRADEMARK_CATALOG_VERSION`, so the trademark check stays off in the
  packaged production setup until you add them. The development `docker-compose.yml` shows all of them.
- **Plans are not billing.** There is no payment, no self-service upgrade and no per-pack quota, and the packs
  `policy-analyzer` and `sheet-connector` are in the plans but not enforced.
- **The console has no saved listings or history yet**, and its editor does not apply several fixes at once.
- **Not built:** the policy analyzer (no call to a real model, no endpoint), the image checker (ADR-008, deferred) and the
  retrieval evaluation (it needs a real run with an embedding provider, so there is no recall figure).
