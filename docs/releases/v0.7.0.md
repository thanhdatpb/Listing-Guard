# Listing Guard v0.7.0

Released YYYY-MM-DD. Changes since v0.6.0. This release moves the API to Spring Boot 4.1 (Spring Framework 7, Hibernate 7,
Tomcat 11, Flyway 12) and documents how a backend in another network or cloud calls the API through Cloudflare Access.
**No endpoint, request, response, `docs/api/openapi.json`, migration, `analysisVersion` or content hash changes**, and there
is no new migration and no new setting: upgrading from v0.6.0 is a backup and a version change. Read the
[upgrade notes](#upgrade-notes) before you deploy. One difference can be seen on the wire (a `404` for an unknown route
loses three `Vary` headers); see [Breaking changes](#breaking-changes).

## What is new

### Platform: Spring Boot 4.1 (ADR-020)

The API moves from Spring Boot 3.5.16 to **4.1.2**. It is a platform change, not a feature.
[ADR-020](../adr/ADR-020-spring-boot-4.md) records why (the fix for two Spring Framework advisories exists only in
Spring Framework 7.0.9 and later), the risks, the verification and the rollback, and amends the "Spring Boot stays 3.5"
decision of [ADR-017](../adr/ADR-017-mcp-server.md).

| Component | v0.6.0 | v0.7.0 |
| --- | --- | --- |
| Spring Boot | 3.5.16 | 4.1.2 |
| Spring Framework | 6.2.19 | 7.0.10 |
| Spring Security | 6.5.11 | 7.1.2 |
| Hibernate ORM | 6.6.53.Final | 7.4.13.Final |
| Hibernate Validator | 8.0.3.Final | 9.1.5.Final |
| Tomcat (embedded) | 10.1.61 (pinned) | 11.0.27 |
| Flyway | 11.7.2 | 12.4.0 |
| springdoc-openapi | 2.10.0 | 3.2.0 |
| Testcontainers (tests only) | 1.21.4 | 2.0.5 |
| Jackson 2 (`com.fasterxml.jackson`) | 2.21.8 (pinned) | 2.21.8 (pinned) |
| PostgreSQL JDBC driver | 42.7.14 (pinned) | 42.7.14 (managed by the Boot BOM) |

The Java level is unchanged (21), and so is the `Dockerfile` (it builds and runs on Temurin 25).

- **Nothing changes for a client.** The same 64 requests (every endpoint, the error cases, `GET /health` and `/v3/api-docs`)
  were sent to `main` before the upgrade and to the upgraded code, on the same data, and the answers compared: status, every
  header and the body with ids and timestamps masked. 62 are identical; the other two are the `Vary` difference in
  [Breaking changes](#breaking-changes). `docs/api/openapi.json` is byte for byte unchanged, and the tests that pin the hash of
  every ruleset, readiness version and the DEMO catalog pass without a pinned value edited. Two differences that Spring
  Framework 7 and springdoc 3.2.0 would have caused are prevented in code: the `title` of a `413` and a `422` problem stays
  "Payload Too Large" and "Unprocessable Entity" (Spring Framework 7 words them "Content Too Large" and "Unprocessable
  Content"), and the four members of Spring's `ProblemDetail` schema that the published contract declares nullable stay
  nullable in the OpenAPI document (one customizer; springdoc 3.2.0 does not read the JSpecify `@Nullable` that Spring now uses).
- **Jackson 2 stays.** The code still uses `com.fasterxml.jackson`, and Spring Boot 4 serializes with Jackson 3 by default (it
  is also on the classpath through Boot's own starter and Flyway). The API keeps the Jackson 2 support Boot still ships
  (`spring-boot-jackson2`, deprecated) and sets `spring.http.converters.preferred-json-mapper` to `jackson2`; without it every
  request body that binds to a Jackson 2 type failed with `500`. The client of the optional `ApiEmbeddingProvider` reads its
  response as bytes and parses it with Jackson 2 for the same reason. The move to Jackson 3 is a separate change (see
  [Known limits](#known-limits)).
- **Security.** The two Spring Framework 6.2 findings that the v0.6.0 notes list as temporarily ignored (`CVE-2026-47884` and
  `CVE-2026-47890`, fixed in Spring Framework 7.0.9) no longer apply, and their `.trivyignore` entries are removed: the release
  workflow now scans the amd64 image with no exception. A local Trivy scan of the new image (critical and high, fixed
  vulnerabilities only, no ignore file) found nothing in the OS packages, the application jar or the other binaries.
- **Pins.** The Tomcat and PostgreSQL driver pins of v0.6.0 are gone: the Boot BOM manages Tomcat 11.0.27 and the same driver
  version. The Jackson 2 pin stays at 2.21.8, for the findings of the v0.6.0 image scan.
- **Nothing to configure.** No setting, environment variable, Compose service or image tag scheme changes. The Spring
  properties that `application.yml` and the production Compose files set keep their names in Spring Boot 4.1.2, the
  `spring.mail.*` ones included.
- **Tests and the `mcp-server` jar.** Test code takes the Boot 4 and Testcontainers 2 packages (no test was weakened, skipped
  or deleted). The `mcp-server` jar is rebuilt on the same SDK (2.1.0, with `mcp-json-jackson2`); the embedded Tomcat of its
  optional HTTP transport is now 11.0.27, and its transport tests (stdio child process, Streamable HTTP, Origin and Host
  refusal) pass on it.

### Calling the API through Cloudflare Access (documentation)

Documentation only: no code, endpoint, `docs/api/openapi.json` or migration changes, and the API still authenticates with
`X-API-Key` alone (Cloudflare Access is configured in Cloudflare, not in Listing Guard). It is for a backend in another network
or cloud that calls the API through the Cloudflare Tunnel of the [Oracle A1 runbook](../deploy-oracle.md).

- **The runbook, section 5.** Access is set up as one self-hosted application per path on the same hostname, each with its own
  policy: `/console/*` for people (an Allow policy on company e-mail addresses), `/api/v1/*` for backends (a Service Auth
  policy with a service token, in addition to `X-API-Key`) and `/health` for the uptime monitor (Bypass, or a token of its
  own). It gives the steps to create a service token (one for each calling backend), its expiry and rotation (rotate with a
  grace period of one hour to 30 days), the account's strict service token setting, the paths that no application covers, and
  curl checks to run from outside the VM.
- **The [integration guide](../integration-guide.md#calling-through-cloudflare-access).** The three headers
  (`CF-Access-Client-Id`, `CF-Access-Client-Secret` and `X-API-Key`), a curl example that reads every secret from an
  environment variable, how to tell a refusal by Access from an RFC 7807 problem of the API (by content type, never by the
  status alone), and timeouts and retries for a client behind Access (`quota-exceeded` is never retried).
- **What it does not claim.** Every statement about Cloudflare cites the page it was read from (on 2026-11-11), and what those
  pages do not say is marked "chưa kiểm chứng (unverified)": the status and body of an Access refusal when strict mode is off,
  the default of the "401 Response for Service Auth policies" option, and what Access does with a path that no application
  matches. The guide is not evidence of a tested Cloudflare Access setup; [ADR-019](../adr/ADR-019-oracle-a1-cloudflare-tunnel.md)
  remains Proposed.

## Breaking changes

None for clients, and no operator action beyond the version change. One difference can be seen on the wire:

- **`Vary` on a `404` for an unknown route.** Such a `404` no longer carries `Vary: Origin`,
  `Vary: Access-Control-Request-Method` and `Vary: Access-Control-Request-Headers`. This is a change of Spring Framework 7; the
  API configures no CORS and nothing in the repository sets these headers, so nothing should depend on them. Every other
  answer, status code and header of the 64 compared requests is the same.

## Upgrade notes

### Database migrations

None. The latest migration is still V27, and no setting is new. Flyway 12.4.0 validated the 27 migrations that v0.6.0 had applied
with Flyway 11.7.2 and logged `Schema "public" is up to date. No migration necessary.`; Hibernate 7 accepted the schema with
`ddl-auto=validate`. This was tried with the published v0.6.0 image and an image built from the v0.7.0 code (amd64), against one
PostgreSQL 16 database that held a check, a variation result and a personalization result stored by v0.6.0.

### Upgrade from v0.6.0

1. Back up the database and keep the dump until the new version has proven itself (see
   [Database backup and restore](../deployment.md#database-backup-and-restore)). Nothing in this release writes to the schema,
   but a backup comes first in every upgrade.
2. Set `LISTING_GUARD_VERSION=0.7.0` in `.env`, then pull and recreate only the API (keep every `-f` file you use, such as the
   Tunnel and shared-network overrides, or set `COMPOSE_FILE` in `.env`):

   ```bash
   docker compose -f docker-compose.prod.yml --profile prod pull api
   docker compose -f docker-compose.prod.yml --profile prod up -d --no-deps api
   ```

   See [Upgrade or roll back an image](../deployment.md#upgrade-or-roll-back-an-image).
3. Check the logs and `/health`. The Spring Boot banner shows v4.1.2, Flyway logs `Successfully validated 27 migrations` and
   `Schema "public" is up to date. No migration necessary.`, and `GET /health` answers `200 {"status":"UP"}`.
4. Send an identical `/api/v1/checks` request twice: the second answer is `cached: true` with the same `checkId`. The cache
   identity does not change in this release, so results stored by v0.6.0 are still answered from the cache. As before, an
   `INCOMPLETE` result is stored but never reused.
5. If you run the optional console, sign in once and open the Check listing page and the API keys page (see
   [Known limits](#known-limits)).

**Coming from v0.5.0 or older?** Read the [v0.6.0 notes](v0.6.0.md#upgrade-notes) first: V22 to V27 run in the same start, and V26
builds indexes concurrently.

### Rolling back

There is no migration to undo, so going back is a version change: set `LISTING_GUARD_VERSION=0.6.0`, pull, and recreate the API
as above. No restore is needed. This was tried on the same database: after the v0.7.0 code had run on it, the v0.6.0 image started,
validated the 27 migrations, answered `/health`, and served and cached the results stored before the upgrade. A backup is
needed only if a later version applies a migration that the older image cannot use.

## Known limits

The [limits of v0.6.0](v0.6.0.md#known-limits) still apply, except the two temporary Trivy exceptions, which this release
removes. New or changed in this release:

- **The Jackson 2 support is deprecated and has an end date.** `spring-boot-jackson2` ships "in a deprecated form and will be
  removed in a future release", and Spring Framework plans to disable Jackson 2 auto-detection in 7.1 and remove its support in
  7.2. The Jackson 3 migration (`tools.jackson`, a pull request of its own) has to be done before the repository moves to Spring
  Boot 4.2. It is on the [README Roadmap](../../README.md#roadmap). The Jackson 2 pin (2.21.8) stays; whether it can be dropped is
  unverified.
- **A customizer keeps the `ProblemDetail` schema as published.** It is removed when springdoc-openapi reads the JSpecify
  `@Nullable` (README Roadmap): delete it and `OpenApiIntegrationTest` must still pass.
- **The upgrade was verified, not load-tested.** The full build (`./mvnw -B verify`, with PostgreSQL 16 in Testcontainers), the
  64-request comparison and an upgrade and rollback on a real database all passed. Memory and speed were not measured against
  v0.6.0, and the sample resource limits are unchanged: watch the API's memory after the upgrade.
- **The `linux/arm64` image was built and its JRE started, but the API was run on amd64 only.** The release workflow builds the
  arm64 image with QEMU for its runtime stage and, as before, scans only the amd64 image with Trivy.
- **The console was verified by integration tests, not by a browser or a real mail server.** Its tests replace the mail sender, so
  sending the sign-in e-mail through a real SMTP server was not exercised after the upgrade (the `SPRING_MAIL_*` names are
  unchanged). If you run the console, test the sign-in, the Check listing editor and the API keys page after upgrading.
- **The Cloudflare Access runbook is documentation.** It lists the points that Cloudflare's pages do not state. The Access
  application for `/console/*` does not cover `/console`, `/login`, `/login/verify` and `/logout`, which the console also serves:
  decide explicitly whether to add them. The MCP server sends only `X-API-Key` (it has no setting for other headers), so it cannot
  call a hostname that Access protects; run it where it reaches the API without Access.

## Image

The release workflow publishes:

- `ghcr.io/thanhdatpb/listing-guard:0.7.0`
- `ghcr.io/thanhdatpb/listing-guard:latest`

Both tags are multi-architecture images for `linux/amd64` and `linux/arm64`. Set `LISTING_GUARD_VERSION=0.7.0` in the production
`.env`. Image tags through `0.5.0` are amd64-only.

The MCP shaded jar is built with `./mvnw -B -pl mcp-server package` and must be attached manually to the GitHub Release as
`listing-guard-mcp-0.7.0.jar`; the release-image workflow only publishes container images.
