# Listing Guard v0.9.0

Released YYYY-MM-DD. Changes since v0.6.0, the last tag. **v0.7.0 and v0.8.0 were not tagged; their content is merged into
this release** (`v0.7.0.md` and `v0.8.0.md` only point here), and so is everything that reached `main` after v0.8.0 was prepared.
**Read the [upgrade notes](#upgrade-notes) before you deploy.**

This is the first release since v0.6.0 that is meant to be pulled and run on the Oracle A1 (arm64) host behind Cloudflare Tunnel
([deploy-oracle.md](../deploy-oracle.md)). It adds the listing checks around the rules (edit mode and history, the review gate of the
batch job, image checks that are off), trademark checks with a client watchlist and a catalog you can build from the Hugging Face
rebuild of the USPTO data, a periodic re-audit, finding feedback and statistics, an optional free-tier LLM step (off), a backtest to
measure the checks, the console in Vietnamese and English on one design system, the Java SDK, the contract and compatibility policy
(ADR-022), and the move to Spring Boot 4.1. It is 220 commits and 15 additive migrations (V28 to V42). **No part of it has run on
ARM64 hardware, on Oracle or behind Cloudflare yet**, and **a real trademark catalog made every one of 20 sample listings `HIGH`**, so
read the first [known limitation](#known-limitations) before you serve one to people.

The API stays at `/api/v1` and every change to it is additive (see [Endpoints and contract](#endpoints-and-contract)). The Amazon
ruleset is now `amazon-2026-12c` and the trademark ruleset `trademark-risk-2026-11b`, so cached Amazon, trademark and
personalization results are computed again once ([What changes in `analysisVersion`](#what-changes-in-analysisversion)).

## What is new

### Listing checks

- **Amazon `description_length`** (ruleset `amazon-2026-12c`): a description over 2000 characters (code points) is a WARNING with the
  count and the number to cut. The number is `unverified` (two old Seller Forums posts, no Amazon page); it is a hint, never an
  ERROR, and has no fix suggestion. `amazon-2026-12b` is kept unchanged. `GET /api/v1/rulesets/AMAZON/limits` lists the limit.
- **Listing input adapters** (ADR-025): a Java module that converts local exports (Etsy listings CSV, Amazon flat file, an
  experimental Shopify-to-Amazon mapping, standard JSON) to the [input schema](../input-schema.md); `GET /api/v1/input-adapters`
  lists the formats. Shopify stays experimental. See [adapters.md](../adapters.md).
- **`batch-check --split-output`**: also writes `passed.csv` and `held.csv`, the rows of your file sorted by whether a person must look
  (an `ERROR`, a trademark result at or above `--hold-trademark-risk`, or a row that could not be checked). The hold is the
  operator's choice, not a legal conclusion, and a passed row is not marketplace approval. See [batch-check.md](../batch-check.md).
- **`GET /api/v1/capabilities`** says what the deployment serves: the packs and their ruleset versions, the state of the trademark
  catalog (`READY`, `DISABLED`, `REFUSED`, and `demo`), whether plans are on and whether fix suggestions are on. It needs a key,
  costs no unit and carries an `ETag`.
- **Image checks** (`POST /api/v1/image-checks`, `GET .../{id}`, ADR-008) are in the API but **off by default**
  (`503 image-checks-not-configured`). The shipped rulesets hold no marketplace threshold, so every check is `INCOMPLETE`; the
  checker does not recognize logos or text in a picture; the bounded decoder and upload staging of ADR-008 are not built, so do not
  switch it on for a caller you do not trust. Images are never stored.
- **Variation checks and personalization screening** (v0.6.0) are unchanged apart from the trademark ruleset below.

### Trademark checks, catalogs and the policy monitor

- **Product type, source links and generic words** (ruleset `trademark-risk-2026-11b`): an optional `product_type` lowers a catalog
  mark whose Nice classes do not include the product's class by one level and says so in `riskAdjustments`; `sourceLinks` link a
  `uspto:<serial>` mark to its TSDR page; a `generic_words` list (shipped empty) caps an ordinary word at LOW. The product types
  and the link pattern are `unverified`. `trademark-risk-2026-11` is kept unchanged.
- **`hf-convert`** (ADR-030): a one-shot job (its own module and image target, DuckDB never in the API image) that converts the public
  Hugging Face Parquet rebuild of the USPTO data, `illeatmyhat/uspto-trademarks`, to a `jsonl-1` file that the unchanged
  `trademark-import` loads. No USPTO key, no database, no network by default. On the dev machine (build data through 2026-10-31) it
  wrote 1,224,122 marks (104 MB) in about one to three minutes; the import loaded 1,040,779 entries in about 5 minutes and 292 MB of
  database. The source is a third party's rebuild: check its terms yourself. Steps:
  [trademark-catalog.md](../trademark-catalog.md#hugging-face-source-hf-convert) and
  [deploy-oracle.md](../deploy-oracle.md#8b-a-trademark-catalog-from-the-hugging-face-rebuild-convert-elsewhere-copy-import-activate).
- **`uspto-convert`** (ADR-009, A2c) converts several daily XML files in one run, keeps the latest transaction of each serial number,
  leaves out marks that are no longer live and filters by Nice class. **`uspto-sync`** (A2d) registers the USPTO zips you download,
  imports a catalog and activates it only after the import succeeded; a rollback goes to the version before. Migration V31 adds the
  append-only activation log, and with `TRADEMARK_FOLLOW_ACTIVATION=true` the API, `batch-check` and `health-report` serve the
  latest activation (a new catalog or a rollback needs no restart). **Both are unverified against real USPTO data, and the ODP
  download is off and unverified.**
- **`tsdr-status`** (ADR-009): a one-shot job that asks the USPTO TSDR whether the marks that findings still name are dead and
  proposes leaving them out of the next catalog. It changes nothing. Off by default; **nothing has talked to the real TSDR**.
  `TSDR_FINDING_STATUS_ENABLED` (off) adds `tsdrStatuses` to a finding.
- **Policy change monitor** (ADR-026): the `policy-diff` job compares policy pages you saved by hand with the previous snapshot of
  hashes and section paths (never the text) and lists the rules that cite a changed page. It downloads nothing and uses no model.

### Client watchlist (ADR-031)

A client keeps its own list of names to watch (team names, nicknames, slogans, marks it received a claim for) and every trademark
check looks for them next to the catalog. A match is a finding with rule `watchlist_match` and `source` `WATCHLIST`, at least `HIGH`
by default (`unverified`). **With no catalog served**, a client that has an enabled entry gets `200` with `catalogStatus`
`NOT_CONFIGURED` and an `INCOMPLETE` result instead of `503`, which is what lets a first deployment use the watchlist before a
catalog exists. `GET` and `PUT /api/v1/trademark-watchlist` (`ETag`, `If-Match`, `412 watchlist-revision-mismatch`); the console has
a Watchlist page with import from a Sheet or a CSV; only an `ADMIN` account changes the list (V38). Guide: [watchlist.md](../watchlist.md).

### Periodic re-audit (ADR-035)

The console page **Rà định kỳ** (`/console/reaudit`) checks the file of the listings you have on sale again, splits the risks into
**new** (a catalog mark or watchlist entry the previous audit did not have) and **known**, tells which listings were edited, added
or dropped, and gives a CSV of what to fix. V40 stores times, versions, SKUs and a hash of each row, never the file or a finding.
The first run of a scope has nothing to compare with, so every risk is known. No endpoint: `HealthReport.reaudit` is additive.
Guide: [reaudit.md](../reaudit.md).

### Edit mode and check history (ADR-033)

`POST /api/v1/listing-edits` runs the listing, trademark and optional variation checks on a listing before and after a revision and
returns changed fields and new, changed and remaining findings. The console editor shows the two versions in two columns; the
**History** page lists the client's retained results with filters (V39 stores references and counts, never listing text). The SDK
has `checkListingEdit`, MCP has a read-only `check_listing_edit`. Guide: [edit-mode.md](../edit-mode.md).

### Feedback and statistics (ADR-034)

Every finding in the console has three buttons (Đúng / Báo nhầm / Không hữu ích) and an optional note of at most 280 characters.
`POST /api/v1/feedback`, `GET /api/v1/feedback/stats`, `HealthReport.feedback`, the **Statistics** page and the weekly home page read
them (V37 stores the verdict and the address of the finding, never listing text). A verdict changes no finding, rule or cache. **The
false-positive rate is what reviewers reported, not a measured precision.** Guide: [feedback.md](../feedback.md).

### Free-tier LLM providers (ADR-036, ADR-037; off by default)

A shared LLM client (Groq, Cloudflare Workers AI, Gemini, in the order you set) and two uses, both console-side and both off:
the **trademark context judge** lowers a MEDIUM catalog finding to LOW when the model says the word is descriptive ("Dodger blue"),
never removes a finding and never raises a level; **rewrite suggestions** (the button *Gợi ý sửa*) show a proposal only when every
rule and the trademark check accept it again, and apply nothing. **Off means no key is read and no request is made.** A provider
gets no listing text until you set its `..._LISTING_TEXT_ALLOWED` after reading its terms. The providers' limits are the free
tiers' and are settings. V41 counts requests; V42 counts rewrite runs. Guide: [llm.md](../llm.md).

### Measuring the value (ADR-032)

The `backtest` job runs the checks over a labelled CSV (claimed yes or no, issue type, mark) and writes recall of claimed listings,
the reason for each miss and the share of unclaimed listings that are flagged (an upper bound on false alarms). The `eval-listing`
job and `ListingEvalGateTest` score 27 synthetic cases per rule, and the build fails when the precision of a `verified` rule falls
below `eval/listing/baseline.json`. Guide: [backtest.md](../backtest.md). **The backtest has not been run on a real labelled file
and the real catalog** (see [Known limitations](#known-limitations)).

### Console and design

- **English and Vietnamese** (ADR-028): every page and the sign-in e-mail, in `messages.properties` and `messages_vi.properties`. The
  default language is `LISTING_GUARD_CONSOLE_DEFAULT_LOCALE` (`en` unless you set `vi`); a reader switches it and the choice is the
  cookie `lg_lang`. The API's answers do not change language.
- **Sign-in through Cloudflare Access** (ADR-027): `LISTING_GUARD_CONSOLE_AUTH_MODE` is `MAGIC_LINK` (default), `CLOUDFLARE_ACCESS` or
  `BOTH`. In the Access modes the API verifies the signed `Cf-Access-Jwt-Assertion` itself and applies its own e-mail or domain
  allow-list; an Access-only deployment needs no SMTP. V35 lets several accounts share one client. **Verified by tests with
  generated keys, not with a real Cloudflare team.**
- **Pages**: home (the week in figures, what needs attention, the data the checks ran on), Check listing, bulk check (paste from a
  Sheet or upload, ADR-029, V36), history, re-audit, watchlist, statistics, report and API keys.
- **Visual identity and design system** (ADR-040, 041, 042): the Listing Guard look on every page (sidebar, the sign-in card, light
  and dark from the system setting, from a phone to a desktop), one finding card everywhere, no color outside the tokens. The brand
  files are public at `GET /brand/**` (no sign-in, no key, no data of a client; cached for a year with a hash of the build) and
  nothing is loaded from a CDN. `console.css` and `watchlist.css` are gone.

### Java SDK, MCP server and extension

- **`listing-guard-client`** (ADR-023): the official Java client (Java 21, Jackson 2, no Spring) with typed calls, typed exceptions for
  the problem answers and a bounded retry; each release tag publishes it to GitHub Packages (workflow `release-client`).
- **MCP server**: now a thin layer on the SDK, nine read-only tools (`check_listing`, `check_trademark`, `check_variations`,
  `screen_personalization`, `get_limits`, `get_usage`, `get_capabilities`, `get_watchlist`, `check_listing_edit`). The jar is attached
  to the GitHub Release by hand.
- **Chrome extension**: another repository, not part of this release. It needs only an API key; the release attaches the contract
  files it copies.

### Platform, deployment and contract

- **Spring Boot 4.1.2** (ADR-020; Spring Framework 7.0.10, Hibernate 7, Flyway 12, Tomcat 11) replaces 3.5.16. Nothing changes for a
  client: 64 requests were compared before and after (62 identical, the other two differ only in `Vary`). The two Spring Framework 6.2
  advisories the v0.6.0 notes carried as Trivy exceptions no longer apply. Jackson 2 stays for now (see
  [Known limitations](#known-limitations)).
- **API contract and compatibility policy** (ADR-022): `docs/api/openapi.json` and `docs/api/input-schema.json` are released
  artifacts; inside `/api/v1` changes are additive only; `./mvnw verify` compares them with the baseline of the last published release.
  Every `/api/v1` response carries `X-Listing-Guard-Version` (the release of the server, `dev` for a local build);
  `listing-guard.api.deprecation.endpoints[]` can add `Deprecation` and `Sunset` headers (empty by default). The release workflow
  attaches `openapi.json`, `input-schema.json`, `contract-sha256.txt` and `compatibility-report.md` to the GitHub Release.
- **The release image builds.** The `Dockerfile` did not copy the `listing-input-adapters` module, so every release build would
  have failed. It does now, and CI builds the image (linux/amd64, not pushed) on every pull request. **Tag only from a commit that
  has this fix** (this one does).
- **Production Compose**: memory caps for the one-shot jobs, the console, plans, fixes, LLM and Access settings forwarded to the
  container, `cloudflared` pinned to `2026.11.0`, and the review of the whole deployment in
  [deploy-readiness.md](../deploy-readiness.md) (section "v0.9.0" holds the checks made for this release).

## What changes in `analysisVersion`

| Pack | v0.6.0 | v0.9.0 | Effect |
|---|---|---|---|
| Etsy listing rules | `etsy-2026-12` | `etsy-2026-12` | unchanged: stored results are still answered from the cache |
| Amazon listing rules | `amazon-2026-12b` | `amazon-2026-12c` | an Amazon listing is checked again once |
| Trademark checks and the trademark part of personalization screening | `trademark-risk-2026-11`, matcher 1 | `trademark-risk-2026-11b`, `matcher-2`, input hash `trademark-input/v2` | checked again once; a catalog imported with `2026-11` is still served (the normalization is unchanged) |
| Variation checks, personalization character rules | `variation-checks-2026-11`, `personalization-screening-2026-11` | same | unchanged |
| Image checks | none | `etsy-image-2026-11`, `amazon-image-2026-11` | every threshold is null, so every check is `INCOMPLETE` |

Two conditional changes: while a client has an **enabled watchlist entry**, the hash of its entries, the watchlist settings
(`trademark-watchlist-2026-11`) and the matcher version are part of that client's trademark `analysisVersion`, so editing the list
makes its next checks new analyses; a client without one keeps the version it had. With the **LLM judge off** (the default) and
`TSDR_FINDING_STATUS_ENABLED` off (the default) a check returns what it returned before, with the same `analysisVersion`. Results
stored before are not returned for a new request; they stay readable by `GET` until they expire (30 days).

## Endpoints and contract

The compatibility check of ADR-022 (`./mvnw -B -pl contract-tools verify`, 105 tests, passed) compares this release's
`docs/api/openapi.json` with the baseline `docs/api/baseline/openapi-v0.6.0.json`: **44 additive changes, 4 other non-breaking, and
3 breaking changes of the document that `docs/api/breaking-changes.yaml` declares and ADR-022 records** (a documentation fix, no
change on the wire; see [Breaking changes](#breaking-changes)). No change is a new breaking change of the API. The
`input-schema.json` is not compared: v0.6.0 has none. The baseline stays `v0.6.0` until this release is tagged (ADR-022).

**New endpoints** (all need an API key; a check endpoint counts against the pack it runs when plans are on):

- `GET /api/v1/capabilities`
- `GET /api/v1/input-adapters`
- `POST /api/v1/image-checks` and `GET /api/v1/image-checks/{id}` (off by default; pack `image-checks`)
- `GET /api/v1/trademark-watchlist` and `PUT /api/v1/trademark-watchlist`
- `POST /api/v1/listing-edits` (runs the listing, trademark and variation packs, so their packs and quota apply)
- `POST /api/v1/feedback` and `GET /api/v1/feedback/stats`

**Additive changes to existing endpoints and schemas:**

- Response headers `X-Listing-Guard-Version`, `Deprecation` and `Sunset` on every `/api/v1` response (the last two only when a
  deployment announces a deprecation, none by default).
- Problem codes `finding-not-found`, `image-check-not-found`, `image-checks-not-configured`, `invalid-feedback`, `too-many-images`,
  `unknown-image-profile`, `unknown-product-type` and `watchlist-revision-mismatch`.
- `POST /api/v1/trademark-checks`: optional request member `product_type`; result members `productType`, `catalogStatus`,
  `skippedRuleIds` and `watchlist`; finding members `start`, `end`, `snippet`, `mark`, `matchType`, `score`, `risk`,
  `insideColorPhrase`, `otherRuleIds`, `sourceIds`, `sourceLinks`, `riskAdjustments`, `tsdrStatuses` (absent unless
  `TSDR_FINDING_STATUS_ENABLED`) and `watchlistEntry`; `source` takes `CATALOG`, `CONTEXT` and `WATCHLIST`.
- `GET /api/v1/reports/summary`: `HealthReport.feedback` and `HealthReport.reaudit`.
- Two schemas are renamed in the document with no wire change: `CheckRequest` to `TrademarkCheckRequest` (the trademark request) and
  `FindingView` to `TrademarkCheckFindingView` (its findings). Generate a client from the file again.

## Breaking changes

**None for the API on the wire.** What a client or an operator can notice:

- **The OpenAPI document changed in three declared places.** The v0.6.0 document typed `TrademarkCheckResult.findings` with the
  schema of `POST /api/v1/checks` findings, so `fix`, `severity`, `value` (and `source` with `RULE` and `LLM`) were declared on a
  trademark finding that never carried them. The compatibility check reports the three removals as breaking **of the document**;
  they are declared in `docs/api/breaking-changes.yaml` and [ADR-022](../adr/ADR-022-api-contract-and-compatibility.md). A client
  generated from the v0.6.0 file should be generated again.
- **Amazon, trademark and personalization results are computed again once** (see
  [What changes in `analysisVersion`](#what-changes-in-analysisversion)).
- **`Vary` on a `404` for an unknown route** no longer carries the three CORS `Vary` values (Spring Framework 7). The API configures
  no CORS, so nothing should depend on them.
- **`uspto-convert`** (an operator tool): its report is `v2` (read `filteredTotal`, `filtered` and `files[]` instead of
  `recordsDropped`, `dropped` and `versionNo`); it keeps only the classes and live status codes of its filters file; a file it cannot
  read no longer stops a multi-file run, it is left out and the run is `INCOMPLETE` (`--strict` stops as before). A catalog already
  imported is not affected.
- **The console looks and is laid out differently** (sidebar, new home page, no shortcuts block, `console.css` and `watchlist.css`
  deleted). Its routes and forms are the same; the pages are not an API.
- Carried over from v0.6.0 for anyone coming from v0.5.0: the Amazon and Etsy ruleset versions, the lower and explicit production
  resource defaults and `--all-clients`; read the [v0.6.0 notes](v0.6.0.md#breaking-changes).

## Upgrade notes

### From v0.6.0

1. **Back up the database** (`deploy/oracle/backup.sh`; see [deploy-oracle.md](../deploy-oracle.md#6-back-up-restore-and-update)). The
   migrations do not undo themselves.
2. Set `LISTING_GUARD_VERSION=0.9.0` in `.env` (**the tag, never `latest`**), then
   `docker compose --profile prod pull api` and `docker compose --profile prod up -d --no-deps api`, keeping every Compose file you
   use (`COMPOSE_FILE` in `.env`).
3. Check the logs and `/health`: the banner shows Spring Boot 4.1.2, Flyway applies V28 to V42, and `GET /health` answers
   `200 {"status":"UP"}`. `curl -sI -H "X-API-Key: $KEY" https://<host>/api/v1/usage | grep -i x-listing-guard-version` must say `0.9.0`.
4. Send an identical `/api/v1/checks` request twice: the second answer is `cached: true`. Etsy results are still answered from the
   cache; Amazon and trademark results are computed again once.
5. **Accounts** (V38): the only account of a `web-...` client becomes `ADMIN` and may change the watchlist; every other account (the
   shared Cloudflare Access client, accounts an operator made) is a `MEMBER`. Promote one with
   `docker compose run --rm admin account role <email> ADMIN`.
6. **Nothing is switched on by the upgrade.** The console, plans, fixes, the image checks, the USPTO sync, the TSDR check, the TSDR
   status on findings and every LLM step stay off until you set their variables.
7. If you build the image or the jars yourself: the repository has new modules (`client`, `listing-input-adapters`, `image-checker`,
   `contract-tools`, `hf-convert`), and the `Dockerfile` copies each by name. Rebuild the MCP jar with
   `./mvnw -B -pl mcp-server -am package`. An image you build yourself says `dev` in `X-Listing-Guard-Version` unless you pass
   `--build-arg LISTING_GUARD_RELEASE=0.9.0`.
8. **A new host** (the Oracle A1 deployment) follows [deploy-oracle.md](../deploy-oracle.md) from the start; the database is empty
   and all 42 migrations run. Coming from v0.5.0 or older? Read the [v0.6.0 notes](v0.6.0.md#upgrade-notes) first: V22 to V27 run in
   the same start, and V26 builds indexes concurrently.

### Rolling back

Restore the pre-upgrade backup **into an empty database**, then set the previous version. **Do not run `deploy/oracle/restore.sh` over
the upgraded database**: it restores with `--clean`, and that failed in the rehearsal (`cannot drop constraint
trademark_catalog_version_pkey ... other objects depend on it`, the foreign keys of V31, V32 and V34). Drop and create the database
first, as [deploy-oracle.md](../deploy-oracle.md#upgrade-from-an-older-release-to-090) describes; that path was rehearsed and worked
(27 migrations, `/health` `200`, the old check readable).

The migrations add tables and columns and loosen three constraints (V29, V35 and V38), so an older image should not be hurt by
them. It was tried once, on a small rehearsal database: the published `0.6.0` image started on the V42 schema, answered `/health`,
returned the stored checks and, with plans on and the client on `SELLER`, answered `/api/v1/usage` and a check. That is one try with
little data and a few endpoints (not the console, not a catalog), so keep the restore as the safe path. Moving back to v0.6.0 also
loses the console pages, the watchlist, history, re-audit and feedback that the newer schema stores.

## Known limitations

The [limits of v0.6.0](v0.6.0.md#known-limits) still apply, except the two Trivy exceptions for Spring Framework 6.2, which the move
to Spring Boot 4.1 removed. What matters most for a first deployment:

- **The false-positive rate against the real catalog has not been measured, and a first look is bad.** No labelled file of claims
  was run against the Hugging Face catalog (`backtest` exists and has not been run on one). What was done before this release is a
  try with 20 invented listings on the real catalog of 1,040,779 entries: **all 20 came back `HIGH`**, 8 `HIGH` findings each with a
  neutral description and 18 with an ordinary sentence, and ten of the twenty had no brand name in them. The `HIGH` findings are
  exact matches of single ordinary words that are registered or pending marks (`MUG`, `BLUE`, `SHIRT`, `GOLD`, `BAG`, and `TO`, `IN`,
  `MADE`, `SHIPS` in a sentence). The converter sets no `common_word`, the `generic_words` list of the ruleset ships empty, and
  `product_type` only lowers a level. **Served as it is, this catalog flags every listing**: decide a generic and short word policy
  before you give it to staff, or use the client watchlist alone. The home page's false-positive rate is what reviewers reported, not
  a precision, and the synthetic evaluation gates only the rules marked `verified`; trademark rules, thresholds and product classes are
  `unverified`. Details: [deploy-readiness.md, section 8](../deploy-readiness.md#the-catalog-measured-on-the-real-hugging-face-build).
- **The time of a trademark check on a catalog of about one million marks was measured on one machine only.** On an amd64 laptop
  (12 CPUs, Docker Desktop), one request at a time, 20 distinct listings of a title, a sentence and five tags each: **average 972 ms,
  p95 1,128 ms** (slowest 1,186 ms); the same listing again is answered from the cache in about 11 ms. It was **not measured on the
  Oracle A1 (2 OCPUs shared with PostgreSQL) or on any arm64 machine**, and not under concurrent load. Importing the catalog took
  1 min 28 s and 404 MB of database for two versions.
- **The `linux/arm64` image has never run on ARM hardware**: the release workflow builds it with QEMU and scans only the amd64 image.
  Before the release it was started once **under QEMU emulation on amd64** (123 s to start, then it answered a trademark check in 4
  to 6 s); that says it starts and works, not how fast it is. Run the smoke test on the A1 before you rely on it. A1 capacity in Tokyo
  was not checked.
- **The personalization rules and the print profiles are placeholders.** `latin_basic` and `latin_extended` use invented values; the
  workshop's real profile is open in [ADR-016](../adr/ADR-016-personalization-screening.md). A personalization finding is a hint,
  and without a catalog its result is `INCOMPLETE`.
- **The image checker recognizes neither logos nor text**, every shipped threshold is null (so every result is `INCOMPLETE`), and the
  endpoint is off and not safe for an untrusted caller until ADR-008's bounded decoder exists.
- **The LLM is off by default and uses free tiers.** The providers' limits are small, a provider may change its terms, a demotion by
  the judge can lose a claimed listing (measure with `backtest --llm-judge` first), and with the rewrite button on a seller's title,
  tags and findings are sent to a third party each time it is pressed. A verified suggestion is not legal clearance.
- **The Vietnamese texts need a native reader.** Every Vietnamese sentence of the console, the rule explanations and the new copy of
  ADR-040 to 042 was written for this work and was not reviewed by a native reader or a lawyer, nor was the English trademark
  statement. The same holds for the Vietnamese report of the `health-report` job.
- **The trademark catalog is only as good as its source.** `hf-convert` is a third party's rebuild of USPTO data whose terms nobody here
  has checked; its filters, the status reading and the class list are `unverified`; the catalog is a snapshot (rebuilt monthly) and a
  mark that dies after it stays in until the next import. `uspto-convert`, `uspto-sync` and the ODP download are unverified against
  real data, and `tsdr-status` has never talked to the real TSDR.
- **The console was verified by integration tests and by looking at screenshots at 375, 768 and 1280 px, not with a real SMTP server,
  a real Cloudflare Access team or a load test.** Sign in once after deploying and walk every page.
- **Console sign-ins are limited by the address of the tunnel connector**, so one person's burst can lock the others out for up to 15
  minutes; requests without a valid key are answered `401` and not rate limited by the application; `/api/v1/*` has no Cloudflare
  Access application (the MCP server sends only `X-API-Key`). The open items are in
  [deploy-readiness.md](../deploy-readiness.md#7-open-items).
- **Jackson 2 support is deprecated** in Spring Boot 4 and has an end date: the Jackson 3 migration has to be done before the
  repository moves to Spring Boot 4.2 (README Roadmap).
- **Memory, CPU and disk on the 2 OCPU / 12 GB host are budgets, not measurements**; the sample caps are unchanged.

## Image

The release workflow publishes:

- `ghcr.io/thanhdatpb/listing-guard:0.9.0`
- `ghcr.io/thanhdatpb/listing-guard:latest`

Both tags are multi-architecture images for `linux/amd64` and `linux/arm64`; only the amd64 image is scanned with Trivy, and the API was
run on amd64 only. Set `LISTING_GUARD_VERSION=0.9.0` in the production `.env` and pull by that tag. Image tags through `0.5.0` are
amd64-only. `hf-convert` is built from the checkout (Dockerfile target `hf-convert`); no release image carries it.

The Java client SDK `com.thanhdatpb.listingguard:listing-guard-client` 0.9.0 is published to GitHub Packages by the `release-client`
workflow. The MCP shaded jar is built with `./mvnw -B -pl mcp-server -am package` and must be attached manually to the GitHub Release
as `listing-guard-mcp-0.9.0.jar`. The release workflow attaches `openapi.json`, `input-schema.json`, `contract-sha256.txt` and
`compatibility-report.md` to a draft GitHub Release that it creates from this file when none exists.
